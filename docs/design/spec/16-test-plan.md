# 16 — Plan de tests

Principe : **les tests sont écrits avant le code de chaque phase**, à partir de cette spécification. Une fonctionnalité est terminée quand ses tests d'acceptation passent.

## 1. Fixtures (dépôts de test)

Chaque fixture est un dossier sous `tests/fixtures/<nom>/` **et** un script `build.sh` qui crée l'historique git (commits, branches) de façon déterministe (`GIT_AUTHOR_DATE` fixé). Aucun historique réel n'est copié. Les chemins listés dans `untracked.txt` de la fixture sont copiés après l'historique, **sans `git add`** : ils sont présents et non suivis dans le dépôt construit (précisé le 2026-11-12, P1.6).

### 2.2 Pilote n°1, test d'acceptation local

- Activé seulement quand la variable `PEO_PILOT1_PATH` désigne un clone local du projet ; sinon ignoré (`skip`). Jamais exécuté en CI.
- Lit ce dépôt en lecture seule ; n'écrit rien, ni dans ce dépôt ni dans celui de PEO.
- Vérifie les traits E1 à E6 (assertions de A1.3, A1.4 et A1.5), pas l'égalité avec un fichier attendu : le projet réel évolue.
- Vérifie aussi les traits A3 (ajout du 2026-11-14, R2) : `inventory()` avec le vrai Runner, `user_config` résolu depuis `CLAUDE_CONFIG_DIR` ou `~/.claude` et `managed = default_managed()` ; sortie conforme au schéma, au moins une source `read`, aucune valeur d'`env` lue dans les réglages (chaîne d'au moins 8 caractères) dans la sortie. Assertions booléennes seulement : pytest n'affiche aucune donnée réelle.
- Aucun fichier, extrait ni sortie de ce test n'est versionné.

### 2.3 Jalon A′, test local (R3)

- Prérequis : le passage `star-segment-*` du spike est joué et la spec 14 §3.5 mise à jour selon son résultat.

- Activé seulement par la variable `PEO_AUDIT_PATHS` (chemins de clones locaux séparés par `:`) ; sinon ignoré (`skip`). Jamais exécuté en CI.
- Lance `peo status --exposure --json` sur chaque chemin, sans rien écrire dans les dépôts audités, avec la version de Claude Code épinglée pour le jalon (la même pour les 3 audits, document 07, section 7.1) ; le test vérifie `inventory.claude_version` et s'arrête si elle diffère. Configuration : un `CLAUDE_CONFIG_DIR` vide pour les clones open source et pour la mesure (b) ; la configuration réelle du poste pour le pilote n°1, désigné par `PEO_PILOT1_PATH` (document 07, section 7.1).
- Vérifie des invariants seulement, pas des constats :
  - durée < 5 s (NF3), temps des sous-processus `claude` exclu : le test les chronomètre à part (Runner enveloppant le vrai) et affiche les deux durées ;
  - aucun accès réseau du processus de PEO (NF5) ; les sous-processus `claude` ne sont pas couverts (limite S20 du jalon) ;
  - aucun message ne contient « protected » ni « protégé » ;
  - aucune valeur d'un `.env*` du dépôt dans stdout, stderr ou le JSON, hors fichiers d'exemple (`.env.example`, `.env.sample`, `.env.template`, `.env.dist`, la liste de Discovery) ; une valeur compte seulement comme mot entier (bornes : début, fin, ou caractère hors `[A-Za-z0-9_-]`). Précisé le 2026-11-15 : des valeurs d'exemple comme `secret` ou `postgres` figurent dans les messages de PEO et donnaient de fausses alertes. Une valeur réelle égale à un mot que PEO écrit lui-même (`postgres`) reste signalée : l'auditeur la juge à la main. Les valeurs sont lues en mémoire par le test ; en cas d'échec, il n'affiche que le nom de la variable.
- Les verdicts d'actionnabilité et la fidélité A/B (document 07, section 7.1) sont notés à la main, pas par ce test : notes brutes dans `docs/dogfooding.local.md` (local, exclu de git), résultats agrégés dans `docs/dogfooding.md` (versionné). Pour un clone open source, `X-SECRET-TRACKED` et `X-LITERAL-IN-AGENT-CONFIG` n'y figurent qu'en comptes (document 07, section 7.1), selon l'état de divulgation du constat (document 07, section 7.1 bis).
- Contrôle automatique de la divulgation (ajout du 2026-11-15) : `tools/check_disclosure.py`, lancé en CI sur `docs/dogfooding.md` et en local par le hook `pre-push`. Règle versionnée : hors de la section « Withheld findings », une ligne qui nomme un dépôt open source du tableau « Repositories » (propriétaire, nom, ou les deux) ne cite ni `X-SECRET-TRACKED`, ni `X-LITERAL-IN-AGENT-CONFIG`, ni `X-SECRET-*`, ni le mot `withheld`. Règle locale : les littéraux de `.git/info/disclosure-denylist` (jamais versionné) n'apparaissent dans aucune ligne ajoutée ni aucun message des commits poussés, ni dans un texte passé sur l'entrée standard (corps de PR) ; un échec ne réaffiche pas le littéral. Le contrôle est lexical : il n'attrape pas une fuite par déduction (une sévérité qui trahit un fichier), que seule la règle de publication du document 07, section 7.1 bis, évite.
- Aucun fichier, extrait ni sortie de ce test n'est versionné. Pour le pilote n°1, `docs/dogfooding.md` ne donne que des comptes agrégés, sous un pseudonyme (section 2.2).

## 4. Niveaux et outillage

| Niveau | Outil | Quand |
|---|---|---|
| Unitaires et propriétés | pytest, hypothesis | à chaque commit |
| Contrats d'adaptateurs | Exécuteur de commandes factice qui rejoue des sorties écrites à la main (`claude plugin list --json`, `uv tool list`, `npm ls -g --json`) | à chaque commit |
| Intégration | Conteneur avec Claude Code, `uv`, Node réels, sur une copie de `fx-split-stack` ; réseau limité aux sources des fiches | chaque nuit et avant une version |
| Bout en bout | `/peo:init` joué à la main sur `fx-split-stack`, puis sur le projet réel du pilote n°1 **avec ton accord**, puis sur le second dépôt existant | jalon MVP |
| Non-régression d'écosystème | Job programmé : versions les plus récentes des outils du socle dans le conteneur, scénario rejoué, issue ouverte si échec | chaque semaine |

## 5. Ce qui ne peut pas être testé automatiquement au MVP

- La qualité des formulations des questions (relecture humaine).
- Le comportement de `claude plugin install` lancé depuis une session (spike S1 : essai manuel documenté).
- La pertinence de la sélection au-delà des fichiers attendus : c'est l'objet des mesures du jalon MVP (document 07, section 6).
